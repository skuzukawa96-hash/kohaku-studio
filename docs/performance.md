# 性能計測の基準値

改善の効果を比較できるよう、計測方法と結果を記録します。
数値は開発機での参考値です（環境により変動します）。

- 対象: v0.4.0 → ストリーミング取り込み導入後（いずれもリリースビルド）
- データ: 200万行 × 8列のCSV（86.5MB。文字列3列 + 整数4列 + 実数1列、5装置 × 5,000ロットの製造データ風）
- 方法: サーバーを起動し `curl` でAPIを呼び、応答時間とプロセスメモリ
  （PowerShell `Get-Process` の WorkingSet / PeakWorkingSet）を記録

## 結果（200万行 / 86.5MB CSV）

| 項目 | v0.4.0 | ストリーミング取り込み後 | 変化 |
| --- | --- | --- | --- |
| **インポート中のピークメモリ** | **905MB** | **238MB** | **-74%** |
| インポート | 11.8秒 | 5.4秒 | 2.2倍速 |
| プロジェクト再読込（Parquetキャッシュ） | 4.8秒 | 3.0秒 | 1.6倍速 |
| プロジェクト再読込（コールド） | 11.2秒 | 5.6秒 | 2.0倍速 |
| 定常メモリ（ロード後） | 133MB | 133MB | 変化なし |
| SQL: COUNT(*) | 0.01秒 | 0.01秒 | — |
| SQL: GROUP BY（5群 / 5,000群） | 3.5 / 1.2秒 | 2.6 / 1.1秒 | やや改善 |
| 分析: プロファイル（100万行上限） | 3.6秒 | 2.7秒 | やや改善 |
| 分析: エルボー法（k=1..10） | 2.2秒 | 1.5秒 | やや改善 |
| 分析: 装置差分析 / SPC / 時系列分解 | 1.5 / 1.2 / 1.8秒 | 1.3 / 1.1 / 1.3秒 | やや改善 |
| Parquetキャッシュのサイズ | 4.9MB | 4.9MB | 変化なし |
| 起動直後のメモリ | 10MB | 10MB | 変化なし |

30万行（13MB）では インポート 1.3秒 / ピーク 144MB（v0.4.0）。

## ストリーミング取り込みで何が変わったか

v0.4.0 の取り込みは「CSV全行を `String` として展開 → 型推定 → `TableData` 全体を構築
→ SQLiteへ一括登録」と、大きな中間データが3世代同時に存在していました。

現在は次の2パス構成です（`csv_conn.rs`）。

1. パス1: 列数・ヘッダー・型推定サンプル（先頭2,000行）だけを収集
2. パス2: 行を直接 `Value` 化し、**5万行ごとのチャンク**で
   SQLite登録とParquetキャッシュ書き込みへ流して即破棄

CSVを2回パースするぶんCPUは増えるはずですが、**実測では逆に2倍以上速くなりました**。
1,600万個の小さな `String` ヒープ確保が支配的コストだったためです
（確保をやめた効果 > 2回パースのコスト）。

## 分析APIの列射影（必要な列だけ読む）

分析APIはソースを全列まとめて `QueryResult`（`Vec<Vec<Value>>`）に読み出していましたが、
実際に使うのは2〜3列だけです。SQL側で列を絞る（`SELECT "x","y" FROM (元のクエリ)`）
ことで、ピークと実行時間の両方が下がりました。

200万行 × 8列に対する、API 1回あたりの**メモリ増分**（取り込み後からの増加）:

| 分析API | 使う列 | 射影前 | 射影後 | 実行時間 |
| --- | --- | --- | --- | --- |
| 時系列分解 | 2列 | +368MB | **+202MB** | 1.25 → 0.67秒 |
| クラスタリング | 2列 | +362MB | **+165MB** | 0.92 → 0.31秒 |
| エルボー法 | 2列 | +354MB | **+156MB** | 1.46 → 0.87秒 |
| SPC管理図 | 2列 | +331MB | **+149MB** | 0.98 → 0.33秒 |
| 回帰分析 | 2列 | +331MB | **+133MB** | 1.01 → 0.40秒 |
| 装置差分析 | 2列 | +293MB | **+111MB** | 1.01 → 0.55秒 |
| データプロファイル | **全列** | +317MB | +317MB（射影できない） | 1.72秒 |
| ロットトレース | 絞り込み済み | +0MB | +0MB | 0.11秒 |

確保・解放するデータが減るぶん、**実行時間も2〜3倍速くなりました**。
射影の前後で全APIの応答JSONが完全一致することを確認しています
（最適化が結果を変えていないことの検証）。

## 残る所見と次の候補

1. **インポートは解決済み**（ピーク238MB）。低スペックPCでも公称上限の200万行を扱えます。
2. **分析APIも大半が半分以下に**。残る最大は**データプロファイルの +317MB**（合計464MB）で、
   全列の統計を出す機能のため列を絞れないのが理由です。さらに下げるなら
   「1列ずつ読んで統計を出し、相関用の数値列だけ f64 で保持する」形にする案があります
   （見込みピーク約120MB）。ただし列ごとにクエリを実行するため、
   ソースが重いSQLのときは実行回数が増えるトレードオフになります。
3. 定常メモリは健全なため、`TableData` の列指向化（大工事）は引き続き不要と判断します。

## 計測の再現手順

```bash
cargo build --release
# サーバーを起動（キャッシュは使い捨てディレクトリへ）
KOHAKU_CACHE_DIR=/tmp/kohaku-bench ./target/release/kohaku-studio --no-browser --port 5594
# 別シェルから curl でAPIを呼び、応答時間とメモリを記録する
```

メモリは `Get-Process -Id <pid>` の `WorkingSet64` / `PeakWorkingSet64` を参照します
（ピークはプロセス開始からの最大値なので、計測の区切りごとに読むこと）。
