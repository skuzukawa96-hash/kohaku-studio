# 性能計測の基準値（v0.4.0）

改善の効果を比較できるよう、計測方法と結果を記録します。
数値は開発機での参考値です（環境により変動します）。

- 計測日: 2026-07-18 / 対象: v0.4.0 相当の main（リリースビルド）
- データ: 200万行 × 8列のCSV（86.5MB。文字列3列 + 整数4列 + 実数1列、5装置 × 5,000ロットの製造データ風）
- 方法: サーバーを起動し `curl` でAPIを呼び、応答時間とプロセスメモリ
  （PowerShell `Get-Process` の WorkingSet / PeakWorkingSet）を記録

## 結果

| 項目 | 30万行(13MB) | 200万行(86.5MB) |
| --- | --- | --- |
| インポート（キャッシュ書き込み込み） | 1.3秒 | 11.8秒 |
| プロジェクト再読込（Parquetキャッシュ） | — | 4.8秒（コールド11.2秒の約2.4倍速） |
| Parquetキャッシュのサイズ | — | 4.9MB（CSVの約1/18） |
| 定常メモリ（ロード後 WorkingSet） | 30MB | 133MB |
| **インポート中のピークメモリ** | **144MB** | **905MB** |
| SQL: COUNT(*) | — | 0.01秒 |
| SQL: GROUP BY（5群 / 5,000群） | — | 3.5秒 / 1.2秒 |
| 分析: プロファイル（100万行上限） | — | 3.6秒 |
| 分析: エルボー法（k=1..10） | — | 2.2秒 |
| 分析: 装置差分析 / SPC / 時系列分解 | — | 1.5 / 1.2 / 1.8秒 |
| 起動直後のメモリ | 10MB | 10MB |

## 所見

1. **定常状態は健全** — 200万行ロード後も133MB（データはSQLite in-memoryが
   コンパクトに保持）。SQL・分析とも数秒以内で、対話的なBI用途に足りる。
2. **唯一の赤信号はインポート中のピークメモリ**で、CSVサイズの約10倍
   （200万行で905MB）。低スペックPC（RAM 4〜8GB）では公称上限の200万行で
   スワップ・メモリ不足の懸念がある。
3. ピークの主因はCSVコネクタの処理順: ①全セルを `String` として展開
   （約16M個の小さなヒープ確保）→ ②型推定後に `Value` の表へ変換 —
   ①と②が同時に存在する瞬間が重い。型推定は先頭2,000行のサンプルしか
   使わないため、①の全行展開は必須ではない。
4. 改善の第一候補は **CSVコネクタ内の2パス化**（先頭2,000行で型推定 →
   本体はストリームで直接 `Value` に変換）。コネクタ内に閉じた変更
   （設計Rule 5）で、ピークを概ね半減できる見込み。さらに下げるには
   チャンク単位のSQLite登録（アーキテクチャ変更）が必要で、費用対効果を
   見て判断する。
